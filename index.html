Tango Controls

Architecture Explained in Plain English

The Big Idea: Everything is a "Device"

Tango Controls is a framework for controlling scientific and industrial equipment — motors, valves, power supplies, cameras, detectors — across a network. It's used at particle accelerators, laser facilities, wind tunnels, and even the world's largest radio telescope (the Square Kilometre Array).

Think of it like a universal TV remote. You press "volume up" and it works regardless of whether the TV is Sony or Samsung. In Tango, every piece of hardware is wrapped in a Device that speaks a common language — hiding all the messy low-level protocols underneath.

The 4 Key Building Blocks

1. Device

The core unit of Tango. Each Device represents one piece of equipment (or a logical group). Think of it as the software face of a physical thing. Every device has three things you can interact with:

ConceptWhat it isExample
AttributesData values you read or writeTemperature, position, speed, voltage
CommandsActions you triggerMove, Reset, Start scan, Stop
StateCurrent status of the deviceON, OFF, MOVING, FAULT, ALARM

2. Device Class

The blueprint or template for a type of device. Like a class in object-oriented programming — you define it once, then stamp out as many devices as you need from it. For example, a Motor class can be used to create 50 individual motor devices, each with its own position and speed, but all sharing the same commands and attributes.

3. Device Server

The actual running program (process) on a computer that hosts one or more Devices. It starts up, registers itself with the database, creates its devices, and then sits waiting for commands from clients. One Device Server can run multiple devices to share memory and system resources efficiently.

Analogy: If the Device is a "waiter", the Device Server is the "restaurant" — it can employ many waiters (devices) and they all share the same kitchen (resources).

4. The Database (Tango Host)

The central registry — the "phonebook" of the entire control system. When a Device Server starts up, it registers itself here. When a client wants to talk to a device, it asks the database "where is device X?" and gets back the network address. This runs on port 10000 and is what you point TANGO_HOST at.

Importantly, once a client gets the device's address from the database, all further communication goes directly to the Device Server — the database is not involved in the actual data flow.

How It All Fits Together

[ Physical Hardware ] e.g. a motor, valve, power supply ↕ [ Device Server ] runs on a computer, wraps hardware as Devices ↕ [ Tango Database ] central registry — knows where everything is ↕ [ Client / GUI ] Jive, Astor, or your own custom application

Device States

Every Tango device always has a state. The standard states are:

StateMeaning
ONOperational and working normally
OFFNot active, but in normal condition
MOVINGIn transition (e.g. a motor travelling to a position)
STANDBYReady but not fully active
RUNNINGActively doing something above normal ON (e.g. acquiring data)
ALARMWorking but something is out of range — operator attention needed
FAULTMajor failure — usually needs hardware intervention or a reset
INITStarting up, not yet ready
DISABLECannot be switched ON due to an external safety condition
UNKNOWNCannot determine state — usually a communication problem

The Management Tools

ToolWhat it does
JiveGUI browser for all devices — explore attributes, commands, and properties. Like a file explorer for your control system.
AstorManages which Device Servers are running on which computers. Start, stop, monitor processes across the whole facility.
TangoTestA built-in dummy device for testing your setup without real hardware.

Communication Under the Hood

Tango uses two protocols internally — you don't need to worry about these, the framework handles it:

  • CORBA — for synchronous communication (you ask, you wait for an answer)
  • ZeroMQ — for asynchronous/event-based communication (subscribe to updates when values change)

Why It Matters

Tango lets you control thousands of pieces of hardware across a network using one consistent API, regardless of what protocols those devices use underneath. A motor controller talking RS-232, a camera using GigE Vision, and a custom VME card all look the same to your client application — they're just Devices with attributes and commands.
